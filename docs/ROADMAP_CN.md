# 后续开发设想

以下均为**计划和建议**，并非当前已实现功能。建议先解决 EXE 操作、配置和
连接可靠性，再优化资源；保持轻量级，避免为了一个状态窗口引入大型 GUI 框架。

2026-10-17 更新：COM 选择、连接检查、CH340 PnP 检查、AI 来源设置和配置热加载
已实现，见 Windows 手册；下表其余配置表单、完整身份握手和升级器仍是计划。

## 第一阶段：把后台程序做成易用的桌面工具

| 优先级 | 改进 | 当前问题 | 建议验收 |
| --- | --- | --- | --- |
| P1 | 原生托盘与状态入口 | 没有托盘，查看状态要重新打开开始菜单；暂停不等于退出 | 显示等待／连接／暂停／异常，提供设置、释放串口、完全退出 |
| P1 | 设置窗口与热更新 | JSON 编辑门槛高；目标、设备配置在启动时读取，暂停／恢复不重新载入 | 表单校验单价、汇率、目标、日志路径；保存后自动生效，错误保留原配置 |
| P1 | 安装／升级／卸载流程 | 运行中的 EXE 不可覆盖，升级要手动结束进程；没有卸载入口 | 安全退出旧进程、备份并原子替换文件、失败回退；支持保留／删除设置 |
| P1 | 设备握手和选择 | CH340 VID/PID 仅识别桥接芯片，不能证明是本设备 | 固件返回设备 ID、版本、协议能力；多设备时明确选择，避免连接其他硬件 |
| P1 | 诊断与串口协调 | 端口占用、无驱动、无日志等问题主要依赖日志；烧录前需手动暂停 | 显示明确原因与重试状态；提供导出脱敏诊断、暂时释放串口 |

托盘建议继续使用 Windows 原生 API，保持后台无浏览器内核。
控制进程与后台可通过简单的本地 IPC 同步配置／状态，避免依赖 PID 文件判断全部状态。
更新器先做手动导入新版包并校验哈希，后续再考虑网络自动更新和签名。

## 第二阶段：测量后再优化资源

当前 EXE 约 7.4 MiB，观察到的后台相关进程合计内存约 55 MiB。
单文件会解压运行时，临时目录和轮换日志也占空间；不能把 EXE 文件大小当成总磁盘占用。

| 优化方向 | 具体建议 | 取舍与验收 |
| --- | --- | --- |
| 日志文件发现 | 当前每次刷新递归枚举会话目录；采用目录变化通知、文件索引与周期补扫 | 10,000 个历史日志场景测量 I/O／CPU，保证归档、午夜、截断不漏计 |
| 首次统计 | 对今日活跃文件建立可失效的轻量缓存，优先恢复偏移与累计状态 | 重启更快；缓存需按日期、文件身份、大小变化验证，不能破坏 fork 去重 |
| 采样与轮询 | 等待设备时降低轮询频率或订阅设备通知；避免不可用温度提供者频繁启动查询 | 测量待机 CPU、唤醒次数和接入延迟；不能令设备数据超过 5 秒失效 |
| 打包方式 | 比较 onefile 与 onedir＋ZIP／轻量安装器；减少不需要的打包模块 | onedir 避免每次解压且可能减少引导进程开销，但文件数量增加 |
| 原生主机 | 若 Python 路径优化后仍不满足要求，再评估 Rust／C++ 版串口与用量读取 | 先移植现有边界测试；开发成本、Windows ABI 和日志兼容性需要维护 |
| 日志策略 | 合并重复状态，限制高频串口输出，保留轮换并提供一键清理 | 长时间异常不刷爆日志，保留足够诊断信息，可选配置日志上限 |
| 资源释放 | NVML 加载／关闭应有清晰生命周期，检查线程退出与串口异常回收 | 连续拔插／暂停恢复后线程、句柄、内存不持续增长 |

先测量空闲、连接、首扫、持续更新、拔插和睡眠唤醒的资源消耗。
候选指标可设为等待设备时 CPU 平均低于 1%，待机相关进程内存争取低于 40 MiB；
这些是待测目标，不能承诺当前架构或所有电脑都达到。

## 第三阶段：数据、兼容性与发布质量

- 价格配置加入生效日期、来源备注和版本，避免修改价格后整天历史用量一起重算。
  如用户需要实际付费金额，使用相应渠道支持的账单来源，与本地估算分开展示。
- 增加昨日／本周／本月汇总和 CSV 导出。先在 PC 展示历史，设备维持简洁主页；
  可选历史数据库需有容量上限、删除和隐私控制。
- 增加 AMD／Intel GPU 和可靠的 CPU 温度提供者。保持这些能力可选；
  不为了一个传感器默认运行需要管理员权限的大型服务。
- 可选手动刷新汇率、每日预算提醒、价格未知提醒。默认保留可解释的固定配置，
  离线时沿用最后确认值，不把估算伪装成实际账单。
- 支持多设备、不同 USB 桥接芯片和明确的固件／主机兼容版本。
  先做协议能力握手，再扩展设备选择。
- 补足 Windows 实际登录、USB 热插拔、串口抢占、24 小时稳定性与升级回滚验收。
  单元测试不能代替物理设备验证。
- 发布带版本信息、SHA-256、许可证和兼容说明的包。逐步完善代码签名和手动确认的
  更新机制；网络更新失败不能影响当前设备工作。

## 设备侧可选方向

保持主页 PC／Codex 监控为核心，优先考虑主题配色、亮度设置、触摸目标优化、
预算进度显示和固件版本信息。只有明确硬件需求时再移植 ESP32-S3，
该迁移涉及芯片目标、引脚、触摸和驱动验证，不只是更改项目名称。

建议下一次开发从“托盘＋真实连接状态＋设置热更新＋退出后台”开始。
这组功能直接改善每天使用和后续升级流程，之后依据基准数据选择打包或原生化优化。
